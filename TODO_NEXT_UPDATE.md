# Партия: 27 потоков в MAX, 99 в VK и слишком длинный журнал (сборка 111)

- **Симптом из лога 110 (OnePlus CPH2645).** MAX работает: `[MAX] Сессия Calls подтверждена` → `Звонок создан` → 27 потоков встали в строй (`Активных: 27`). Но в настройках больше 27 не выставить, в VK — больше 99, а журнал на 553 строки почти целиком состоит из повторов.
- **Причина №1 (MAX 27).** `SettingsTab` считал потолок ползунка через `WorkerCountPolicy.maximumForSources(...)`, где `manualHashCount` для MAX равен 1 → `1 × GROUPS_PER_VK_HASH(3) × WORKERS_PER_GROUP(9) = 27`. У MAX нет VK-хешей, лимит по хешам к нему неприменим.
- **Причина №2 (VK 99).** `WORKERS_PER_GROUP = 9` в Kotlin, а в нативном клиенте `rust-client/worker.rs` — 10. Ползунок шёл по 9 до последней ступени ≤100, то есть до 99, а клиент всё равно пересчитывал в десятки.
- **Причина №3 (двойной журнал).** `TunnelManager` пишет каждую строку процесса в `FullLog` как `[клиент]`, а затем разобранное сообщение — как `[приложение]`. Отсюда по две одинаковые строки на каждый шаг; в логе 110 так задвоены ~40 % строк.
- **Правка №1 (`Constants.kt`).** `WORKERS_PER_GROUP = 10`, `GROUPS_PER_VK_HASH = 3`, `MAX_WORKERS = 100`, `DEFAULT_MAX_WORKERS = 100`, `DEFAULT_WORKERS = 20`.
- **Правка №2 (`WorkerCountPolicy.kt`).** Новый `maximumForTransport(maxMode, jitsiMode, …)`: у MAX и Jitsi потолок — `MAX_WORKERS` (100), у VK — по числу хешей (30/60/90/100).
- **Правка №3 (`SettingsTab.kt`).** Ползунок использует `maximumForTransport`; в MAX доступны все 100.
- **Правка №4 (`FullLog.kt`).** Повтор строки клиента от приложения в пределах 1 с не пишется; строки клиента сохраняются все. Тест `FullLogTest`.
- **Правка №5 (`turn.rs`, `session.rs`).** Флаг `verbose` у `TurnConnectTarget`/`TurnAllocation`: подробные шаги (`Транспорт`, `Аллокация активна`, `ChannelBind`, `Refresh`, `Сессия готова`) — только для первых трёх потоков. `[READY] Поток готов ✓` из Rust убран (дублировал событие приложения).
- **Правка №6 (`max_tcp.rs`).** Строка про новый токен сессии — `report_once` и без метки ошибки; «распаковка: флаг → кодек» одной строкой вместо двух.
- **Правка №7 (`stats.rs`).** Убрана строка `[СТАТИСТИКА]` из клиента: приложение печатает `[СЕТЬ]` по тому же событию.
- **Правка №8 (`max_calls.rs`, `TunnelManager.kt`).** `call token получен` — один раз за процесс; в MAX звонок подписывается `[MAX] Звонок создан ✓`, а не «VK JS».
- **Проверить живьём (111):** в настройках MAX ползунок доходит до 100; в логе `воркеров=100` (если сеть позволяет), нет парных строк `[клиент]`/`[приложение]` с одинаковым текстом.

# Партия: бесконечный «early eof» в журнале MAX (сборка 109)

- **Правка №3 (`main.rs`).** `max tcp: соединение потеряно`, `max tcp: чтение заголовка`, `early eof` добавлены в сетевые маркеры → переподключение, а не фатал.
- **Тесты.** `closed_connection_stops_the_wait_loop_at_once` (duplex-сокет закрыт → ошибка сразу), `only_decode_errors_are_skippable`, `dropped_max_connection_is_retried_not_fatal` (main.rs).
- **Проверить живьём (109):** при обрыве в журнале одна строка «соединение потеряно на opcode N» и далее переподключение; лавины «early eof» быть не должно.

# Партия: LZ4-смещение читалось как big-endian (сборка 106)

- **Симптом из лога 105.** `[MAX][TCP] ← cmd=1 opcode=6 флаг=0x01 220Б` (читается) → `← cmd=1 opcode=19 флаг=0x03 16128Б` → `MAX TCP: распаковка opcode 19 (флаг 0x03): MAX TCP: LZ4 неверное смещение 6656`.
- **Причина.** `6656 = 0x1A00`; при обратном порядке байт это `0x1A` = 26, валидное смещение. LZ4 хранит смещение little-endian, код читал big-endian. На INIT (220 Б) все смещения < 256 → байты совпадают, ошибка не проявлялась.
- Стоп-кадр: вторая попытка в том же логе получила `cmd=3 opcode=19 login.cred` — то есть первый LOGIN сервер ПРИНЯЛ, и токен после него уже невалиден. Это следствие, а не причина.
- **Правка №1 (`max_tcp.rs`).** `lz4_block_with(input, little_endian)`; `lz4_block()` = BE-вариант для совместимости. Хвост нулей трактуется как выравнивание (break), а не как данные.
- **Правка №2 (`max_tcp.rs`).** `decode_frame(payload, flag)` — перебор способов распаковки с проверкой разбором MessagePack: `lz4-le`, `lz4`, `zstd`, `lz4-size` (4 байта префикса), `lz4-skip2`, `raw`. Первый успешный используется.
- **Правка №3 (`max_tcp.rs`).** `report_decoder()`: одна строка на пару «флаг → кодек», предупреждение при несовпадении с ожидаемым по флагу; в `decode_frame` — строка, если в LOGIN есть новый токен.
- **Тесты.** `lz4_offset_is_accepted_in_both_byte_orders`, `compression_flag_selects_the_right_codec`.
- **Проверить живьём (106):** в журнале `распаковка: флаг=0x03 → lz4-le`, затем запрос `158` и создание звонка; `login.cred` на второй попытке быть не должно.

# Партия: MAX падал на LZ4 при валидном токене (сборка 105)

- **Симптом из лога 104.** `07:25:48 [MAX] Транспорт приложения не сработал: MAX TCP: LOGIN: MAX TCP: LZ4 неверное смещение 6656`, следом все адреса `ws-api.oneme.ru` / `ws-api.max.ru` в таймаут TCP. Вторая попытка через 30 с дала уже `login.cred` — то есть первая попытка падала ДО проверки токена, на распаковке.
- **Причина.** Флаг сжатия в старшем байте длины: `0x00` — без сжатия, `0x01..=0x7f` — LZ4, `0xff` — zstd. Маленький INIT влезал в LZ4, а большой LOGIN-ответ приходит zstd. Код читал только бит 24 (`& 0x0100_0000`) и всегда звал `lz4_block`, поэтому на zstd получал «неверное смещение».
- **Правка №1 (`max_tcp.rs`).** `decompress_payload(input, flag)`: `0xff → zstd_block`, `0x01..=0x7f → lz4_block`, `0x00 → как есть`, неизвестный флаг — оба кодека с общей ошибкой. `zstd_block` через `zstd::bulk::decompress` с лимитом `MAX_DECODED_BYTES`.
- **Правка №2 (`Cargo.toml`).** Зависимость `zstd = { version = "0.13", default-features = false }` (в lock уже была транзитивно).
- **Правка №3 (`max_tcp.rs`).** Лог каждого принятого кадра: `[MAX][TCP] ← cmd=… opcode=… флаг=0x… …Б`.
- **Тест.** `max_tcp::compression_flag_selects_the_right_codec` (zstd, raw, LZ4, неизвестный флаг).
- **Из лога же:** `ws-api.oneme.ru` и `ws-api.max.ru` у оператора недоступны (таймаут TCP), а `api.oneme.ru:443` открывается — значит основной путь MAX сейчас TCP, WS остаётся резервом.
- **Проверить живьём (105):** MAX должен пройти LOGIN без «LZ4 неверное смещение»; в журнале будет строка `[MAX][TCP] ← cmd=1 opcode=19 флаг=0xff …`, затем запрос 158 и создание звонка.

# Партия: вход в ВК падал на «web_token: VK не выдал access_token» (сборка 93)

- **Симптом.** Нажал «Войти через приложение» → открылось приложение ВК → вернулся в MRTT → «Не удалось получить VK токен: web_token: VK не выдал access_token». Закрыл окно, попробовал снова — та же ошибка, войти невозможно вообще.

# Партия: картинки с первого раза, Adblock не ломает YouTube (сборка 89)

- **Симптом №1 (Adblock + YouTube).** При включённом Adblock на YouTube не грузились картинки и прочее; выключил — всё грузится; включил обратно — работает, но после повторного захода снова ломается.
- **Причина №1.** `youtube_ads::is_ad_sni` рвал TLS по шаблону SNI «одна `r` + цифры + `---`» (`r1---sn-…googlevideo.com`). Такие имена отдают не только рекламу: с тех же кэшей приходят превью, постеры и обычные куски ролика. Каждый обрыв — потерянная картинка; «второй заход работает» потому, что запрос попадал на другой узел. Плюс `redirector.googlevideo.com` был и в `AD_HOSTS` (обрыв по SNI), и в самом `adblock.txt` — он маршрутизирует выдачу видео.
- **Правка №1.** `AD_HOSTS` сужен до `s.youtube.com`, `ad.youtube.com`, `pagead2.googlesyndication.com`; `is_ad_sni` больше не смотрит на CDN (шаблон оставлен как `#[cfg(test)]`-справка); `redirector.googlevideo.com` удалён из `adblock.txt`; в `adblock.rs` добавлен `CONTENT_HOSTS` (`redirector.googlevideo.com`, `manifest.googlevideo.com`, `youtubei.googleapis.com`), который `is_blocked` не блокирует никогда — даже если адрес придёт из скачанной подписки.
- **Причина №2 (DNS-фильтр).** На заблокированный домен уходил NXDOMAIN (rcode 3, 0 ответов). Часть приложений (Telegram, YouTube при загрузке превью) на «имени не существует» уходит в ветку «сеть недоступна» и останавливает загрузку до ручного повтора.
- **Правка №2.** `build_nxdomain` заменён на `build_empty_answer(payload, question, response, with_soa)`: код 0, 0 записей в ANSWER, запись SOA в AUTHORITY (TTL 10 с) — штатный NODATA, как у AdGuard/Pi-hole. Маленький буфер теперь отказ (`None`), а не обрезанный пакет. Обновлён вызов в `dispatcher.rs::try_answer_blocked_dns`. Тесты: `builds_empty_answer_with_echoed_question`, `empty_answer_without_soa_is_shorter_and_still_valid`, `tiny_buffer_is_refused_instead_of_cut`.
- **Причина №3 (главная для «не догружается»).** В `turn.rs` пакет, не поместившийся в очередь приёма (128 слотов), молча выбрасывался вместе с буфером; в `turn_stream.rs::copy_channel_data` кадр, на который не нашлось буфера в пуле, отдавался как `DataDropped`. Это потеря уже после расшифровки, перед сдачей в TUN: TCP повторяет только по тайм-ауту, пользователь видит «не догрузилось, нажал ещё раз».
- **Правка №3.** `deliver_incoming` (async) ждёт места до 1 с шагом 2 мс и только потом уступает (`queue_full_drops`); `copy_channel_data`/`decode_frame`/`take_frame`/`read_frame` стали async и ждут свободный буфер до 250 мс (`DataDropped` остаётся последним средством). `process_packet` стал async, вызовы в `driver_loop_udp`/`driver_loop_stream` обновлены, комнатный путь (Jitsi) тоже сдаёт пакеты через `deliver_incoming`. Тесты: `incoming_packet_waits_for_room_instead_of_being_dropped`, `channel_data_waits_for_a_pool_buffer_instead_of_dropping`.
- **Причина №4 (сборка фрагментов).** `Reassembler` искал свободный слот только в 8 позициях из 512 (`REASSEMBLER_PROBE_MAX = 8`) и держал сборку 300 мс. На загруженном канале все 8 оказывались заняты — фрагмент терялся, а пакет крупнее MTU (картинка/кусок видео) не собирался.
- **Правка №4.** `REASSEMBLER_PROBE_MAX = REASSEMBLER_SLOTS` (весь набор), `REASSEMBLER_TIMEOUT_MS = 2000`. Тест `test_frag_finds_a_slot_in_a_busy_reassembler`; тест таймаута переведён на константу.
- **Причина №5 (главная для «Adblock включён — интернета нет»).** `try_reset_encrypted_dns` рвал **весь** DoT (порт 853), пока фильтр активен. При системном «Приватном DNS» (Android 9+) это ломает разрешение имён у всех приложений сразу. Отсюда «включил Adblock — не грузит, выключил — грузит».
- **Правка №5.** `adblock::encrypted_dns_blocking()` — DoT режется только при включённом наборе `geosite-category-doh`; DoH по SNI режется как раньше. `mark_categories` принимает `impl AsRef<str>`. Тест `encrypted_dns_port_cut_needs_the_explicit_category`.
- **Причина №6 (мелочь).** `TurnReceiver::recv` при `rearm_notification() == true` начинал цикл заново (`continue`) и терял лишний проход; пакет, пришедший между проверкой и подпиской, ждал следующего пробуждения.
- **Правка №6.** Сброс флага без `continue`, повторная проверка очереди перед `select!`.
- **Тексты в приложении.** `AdblockInfoDialog`/`AdblockTab`/`AdblockPolicy`: вместо NXDOMAIN — «пустой ответ», вместо «DoT/DoH рвётся всегда» — «DoT рвётся только при наборе „Шифрованный DNS“», упомянуто, что адреса маршрутизации видео не блокируются.
- **CI.** Один прогон `44369059099` — зелёный целиком (Android unit-тесты, Rust x86_64/arm64/armv7, Linux клиент и сервер, APK, публикация релиза); релиз `mrtt-1.0-beta1-89` (universal 55.8 МБ, arm64 43.6, armv7 42.9, x86_64 44.1).
- **Проверить живьём:** (1) YouTube с включённым Adblock: зайти два-три раза подряд, прокрутить ленту — превью на месте, ролик играет, реклама в начале не появляется; (2) Telegram: открыть чат с медиа, дождаться загрузки фото/видео с первого раза, без повторного нажатия; (3) при включённом «Приватном DNS» (Настройки → Сеть → Приватный DNS = «Авто»/провайдер) и включённом Adblock сайты открываются, имена резолвятся; (4) включить набор «Шифрованный DNS» — и только тогда DoT-обход режется (`[ADBLOCK] Шифрованный DNS обойдён` в журнале).

# Партия: воркеры и сторож тишины (сборка 88)

- **Симптом.** «ВОРКЕР #71/#73/#75/#77/#79» + «Ошибка (попытка 1): поток N: 64 секунд без ответов сервера через звонок» и «TURN UDP transient receive error, retrying: Connection refused (os error 111)».
- **Причина №1 (ложный таймаут).** В `writer_loop` (`rust-client/session.rs`) keepalive жил как `tokio::time::sleep(10s)` внутри `tokio::select!`: таймер пересоздавался на каждой итерации, а при постоянной очереди данных (`commands.recv()` всегда готов, к тому же `biased`) до ветки сна дело не доходило. Эхо-пинг не уходил → сервер не отвечал `PATH_ECHO` → `watch_silence` через `SILENCE_LIMIT_ECHOED=60s` рвал сессию. Отсюда ровно «64 секунды» и пачка потоков сразу.
- **Правка №1.** `tokio::time::interval_at(now + KEEPALIVE_INTERVAL, KEEPALIVE_INTERVAL)`, ветка keepalive стоит в `select!` **до** `commands.recv()`, добавлена ветка `shared.probe.notified()` для внеплановой проверки пути сторожем.
- **Правка №2 (терпение).** `SILENCE_LIMIT_ECHOED` 60 → 90 с, `SILENCE_LIMIT_PLAIN` 120 → 150 с; `watch_silence` рвёт сессию только после двух окон подряд, между ними шлёт `probe` и пишет «[СЕССИЯ #N] Тишина N секунд, проверяем путь через звонок». Правило решения вынесено в `silence_is_fatal(echoed, quiet, now, sent, inbound)` — покрыто тестом.
- **Причина №2 (Connection refused).** `UdpReceiveErrors::tolerate` считал `ConnectionRefused` временным до 16 раз в окне 5 с — это ICMP «порт закрыт», то есть мёртвая аллокация; клиент вместо пересоздания ждал тайм-аутов.
- **Правка №3.** `UDP_CONNECTION_REFUSED_LIMIT = 3`: после трёх отказов подряд `tolerate` возвращает «не временная», воркер пересоздаёт аллокацию. Лог ограничен `UDP_TRANSIENT_LOG_WINDOW = 30s` (раньше писал только о первом отказе в серии). Тесты: `transient_udp_receive_errors_are_bounded_until_a_receive_succeeds`, `successful_receive_resets_refusal_counter`, `silence_watch_tolerates_busy_tunnel_and_empty_one`.
- **CI.** run `44307423490` — зелёный целиком (unit-тесты, Rust x86_64/arm64/armv7, Linux клиент/сервер, APK); релиз `mrtt-1.0-beta1-88`.
- **Проверить живьём:** (1) покачать на полной скорости 10+ минут — в журнале не должно быть «без ответов сервера через звонок», счётчик потоков ровный; (2) подержать телефон в плохой сети (метро/лифт) и вернуть — туннель восстанавливается сам, без пачки ошибок по всем воркерам; (3) если сервер перезапустить, поток поднимается за секунды («Connection refused» не спамит).

# Партия root-hide: скрытие портов через root с fallback на обычный режим

- **Что добавлено.** `RootShell` (единственное место с `su`: проба `id`, таймауты 4 с на пробу и 8 с на команду, кэш ответа), `PortHidePolicy` (чистая сборка правил iptables/ip6tables + тексты статуса), `PortHide` (применение/снятие правил, переименование процесса клиента, состояние в `filesDir/port-hide-uids.txt`), `AppMultiPickerDialog` (выбор приложений галочками, переиспользуемый).
- **Как работает скрытие порта (как в NekoBox).** На `OUTPUT` для UID выбранных приложений ставится `-d 127.0.0.1/32 -j REJECT` (и `::1/128` для ip6tables), плюс `sysctl -w net.ipv4.conf.all.route_localnet=1`. Свой UID и UID 0/1000 исключены: клиент сам ходит на loopback. Правила ставятся перед стартом клиента (`TunnelManager.startProcessLocked`) и снимаются в `stopLocked` — всегда, независимо от текущего состояния root.
- **Процесс.** `PortHide.maskProcessName(pid)` пишет `kworker/u2` в `/proc/<pid>/comm` и `/proc/<pid>/task/<pid>/comm` — без root `libclient.so` в `ps` это готовый отпечаток.
- **Fallback.** `RootShell.isAvailable` кэшируется; в UI `rootAvailable == false` даёт текст «Root не выдан · обычный режим: порт случайный, но локально доступен» и переключатель недоступен. Обычный режим (порт 0, `setSession("VPN")`, `VISIBILITY_SECRET`, `-stealth`) не менялся.
- **Событие `LOCAL_PORT`.** Rust теперь отдаёт реально занятый порт отдельным событием (`events.local_port`, `TunnelEventParser.Event.LocalPort`), а не строкой лога: в режиме скрытия порт не должен попадать в журнал/уведомление, но приложению он нужен. `encode_event` стал `pub(crate)`, добавлен тест.
- **Настройки.** `port_hide_root` и `port_hide_packages` — глобальные (не на профиль), входят в экспорт/импорт JSON (`port_hide_root`, `port_hide_packages`).
- **Тесты.** `PortHidePolicyTest`: правила на IPv4/IPv6 для каждого UID, исключение своего UID, отбрасывание 0/1000 и дублей, разные формы `-I`/`-D`, `set +e` и `MRI_OK`, разбор/склейка UID, тексты статуса.
- **Ограничение.** Root-режим не прячет сам факт VPN-интерфейса от чужих API — это делают LSPosed/Zygisk/ядро (как VPN Hide у NekoBox-пользователей), в APK без модулей это невозможно. В подсказке это написано прямо.
- **CI:** run 44281345526 (коммит `1ceda59`) — зелёный целиком (unit-тесты, Rust x86_64/arm64/armv7, Linux-клиент и сервер, APK); релиз `mrtt-1.0-beta1-81` (universal 53.1 МБ, arm64 41.6, armv7 40.9, x86_64 42.0). Первый прогон упал на 429 от Maven Central (`compose-group-mapping-2.4.0.pom`) — это rate limit, а не код: перезапуск прошёл. По пути поправили `AppItem` (пакет `com.mrtt.client.ui`, а не `ui.apps`) и ожидание в тесте снятия правил.
- **Проверить на живом профиле (с root):** (1) включить «Скрывать порты и трафик» → «Скрытие через root», выбрать приложение, подключиться; в логах `[ROOT] localhost закрыт для N приложений`; у выбранного приложения `curl 127.0.0.1:порт` не проходит; (2) `ps -A | grep libclient` не находит клиент; (3) отключить VPN — правила сняты (`iptables -L OUTPUT -n` пуст по этим UID), приложение снова видит localhost; (4) без root — переключатель недоступен, туннель работает как обычно.
